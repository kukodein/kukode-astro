# Kukode Web

## PRD — WordPress-to-Static Migration Stack

A reusable technical reference for migrating a WordPress site (or building a new
one from scratch) onto a fully free-hostable, static-first stack. Replace
bracketed placeholders when reusing this for a new project.

### 1. Goal

Move a WordPress site off paid shared hosting onto a stack that:
- Costs $0 to run at low/medium traffic
- Is SEO-friendly by default (SSG, not client-rendered)
- Can be updated by a non-technical or semi-technical owner without touching code
- Deploys automatically from a Git repo

### 2. Tech Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | [Astro] (SSG mode) | Ships minimal JS by default, first-class i18n routing, ideal for content-heavy sites |
| Data source / CMS | Google Sheets, read via CSV export URL (`/export?format=csv&gid=`) | Zero-auth for public content, familiar spreadsheet UI for the site owner, no server/DB to run |
| Styling | [Bootstrap 5.3, heavily overridden via CSS custom properties] | Project-specific — swap for Tailwind/plain CSS as needed |
| Hosting | Vercel (or Netlify / Cloudflare Pages — all free-tier static hosts work) | Free tier, Git-connected auto-deploy, keeps last successful deployment live if a new build fails |
| Rebuild trigger | GitHub Actions scheduled workflow (`cron`) → Vercel Deploy Hook | Free, unlimited schedule granularity (unlike Vercel Cron Hobby tier, which is capped at once/day) |
| Images | External hosting, URL stored in the sheet | Keeps the repo/build lightweight; no image pipeline to maintain |

### 3. Data Flow

```
Google Sheets (content source)
   │  fetch at BUILD TIME (not in-browser)
   ▼
Astro build process (getStaticPaths / component frontmatter)
   │  in-memory cache dedupes repeat fetches of the same tab within one build
   ▼
Static HTML, one per page × per locale
   │
   ▼
Deployed to Vercel
```

Rebuild trigger flow:
```
Owner edits Google Sheet
   │ (no live push — waits for schedule)
   ▼
GitHub Actions cron (interval per project needs)
   │ POST
   ▼
Vercel Deploy Hook → re-fetches Sheets → rebuilds → deploys
```

### 4. Sheet Schema Pattern

Two conventions, pick per content type:

- **Key-value rows** (`page | key | value` or just `key | value`) — for settings
  and low-structure content (site settings, per-page metadata). Flexible,
  add fields without a schema change.
- **Fixed columns** — for repeating, structured content (blog posts, nav
  items). Faster to query, but adding a field means adding a column.

Cross-language linking: use a stable `*_id` column (not the slug) to connect
the same piece of content across language tabs, since slugs are translated
and won't match 1:1.

### 5. i18n Routing

- One locale is default with no URL prefix; other locales get a path prefix
  (e.g. `/id/...`). Astro's built-in i18n config handles this
  (`prefixDefaultLocale: false`).
- hreflang tags need explicit per-locale paths passed to the SEO
  component — do not assume the same path across locales (article slugs in
  particular usually differ per language).

### 6. SEO Checklist

- Canonical URL — derived from the current page's own path
- `robots` meta tag — default `index, follow`; add per-page override only if
  a real need for `noindex` shows up
- `X-Robots-Tag` HTTP header — set via hosting platform config (e.g.
  `vercel.json` → `headers`), as a second layer alongside the meta tag
- Open Graph tags — cover title, description, image, url, site_name, locale;
  LinkedIn has no separate tag standard — it reads Open Graph
- Twitter/X Card — `summary_large_image` + title/description/image
- `article:published_time` / `article:modified_time` + JSON-LD `Article`
  schema for blog content
- `robots.txt` + XML sitemap (auto-generated by `@astrojs/sitemap` if using
  Astro) — note sitemap's automatic hreflang-by-path-matching only works
  for pages with identical paths across locales; per-page `<link
  rel="alternate">` tags remain the source of truth for anything else

### 7. Reliability Notes

- Fetches from the CMS source should retry (2–3 attempts) before failing the
  build, to absorb transient network blips
- A failed build does **not** take the live site down on Vercel/Netlify —
  the last successful deployment stays live. Design the failure path around
  this instead of building a custom fallback-data mechanism (an in-repo
  fallback snapshot only works if it's actually committed back to the repo,
  which a build step alone won't do)

### 8. Known Trade-offs

- CSV-export-URL data fetching means the sheet must be shared as "anyone
  with the link can view" — fine for content that's going to be public on
  the site anyway, wrong choice if any row needs to stay private
- Scheduled rebuilds cost build minutes even when nothing changed — fine at
  low change-frequency; reconsider the interval if it starts eating into a
  free-tier build-minute quota
- Hardcoded (non-Sheet-driven) page sections mean duplicate maintenance
  across languages — pick this only when the content genuinely won't need
  frequent edits

### 🚀 Project Structure

Inside of your Astro project, you'll see the following folders and files:

```text
/
├── public/
├── src/
│   └── pages/
│       └── index.astro
└── package.json
```

Astro looks for `.astro` or `.md` files in the `src/pages/` directory. Each page is exposed as a route based on its file name.

There's nothing special about `src/components/`, but that's where we like to put any Astro/React/Vue/Svelte/Preact components.

Any static assets, like images, can be placed in the `public/` directory.

### 🧞 Commands

All commands are run from the root of the project, from a terminal:

| Command                   | Action                                           |
| :------------------------ | :----------------------------------------------- |
| `npm install`             | Installs dependencies                            |
| `npm run dev`             | Starts local dev server at `localhost:4321`      |
| `npm run build`           | Build your production site to `./dist/`          |
| `npm run preview`         | Preview your build locally, before deploying     |
| `npm run astro ...`       | Run CLI commands like `astro add`, `astro check` |
| `npm run astro -- --help` | Get help using the Astro CLI                     |
